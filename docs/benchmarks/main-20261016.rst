kernel selection is used. NumPy 2.2.6, SciPy 1.15.3 and Torch 2.8.0+cpu /
2.8.0+cu128 use separate project-local CPU/CUDA environments.

Every configuration uses seed 20261015 and three warmups. Implementation
candidates use standard CG, fused native operations, rtol=1e-8, atol=1e-12,
maxiter=2000 and true-residual
refresh/restart every 50 updates. Dense repeats three solves per round;
CSR repeats one. Thirty requested Williams rounds remain 30 for two, three
or six candidates; the four-candidate BLAS configuration completes 32 rounds.
Pass one executes the configurations forward and pass two reverses them.

Each cell is the **median of the two process medians**, in milliseconds,
followed by **[minimum–maximum process median]**. Each process median uses
round-average completed wall times. The bracket is neither a confidence
interval nor individual-call tail latency. Two launches are limited evidence
of process variance; no statistical significance or universal speedup is claimed.

Native and matching-policy prepared candidates reuse output/workspace/Jacobi
and charge every x0 reset. API charges per-call output/workspace/Jacobi
allocation and setup. Official SciPy CG allocates iterative workspace in both
scopes and follows its own residual policy. CUDA inputs
are resident, with completion fences; uploads/snapshots, canonical CSR
conversion and correctness downloads are excluded. Torch uses eager public
operations implementing this project's matching-policy CG, not an official
Torch CG solver, ``torch.compile`` or CUDA Graphs. SuperLU total/reuse and
official SciPy CG/PCG remain strategy comparisons with their own stopping
and allocation policies. LU reuse excludes factorization in both scopes.
Do not subtract separately measured API/prepared medians to isolate a phase.
See :doc:`methodology` for the full timing, storage and accuracy contracts.

The work column gives iteration/matvec counts. A single value is shared by
all candidates and both processes; otherwise labels identify the differences.
N=native, B=BLAS/cuBLAS, NP=NumPy, S=SciPy-out, T=Torch; NCG/NPCG and
SCG/SPCG denote native and official SciPy CG/PCG; LUT/LUR denote LU total/reuse.
``max R/tol`` is the largest independent residual/threshold ratio among
that row's candidates and both processes. Different counts mean different
numerical work despite shared recurrence; those are times to accepted
solutions, not equal-work kernel speedups.

The following public ``make pyprof`` commands reproduce all 52 fixed profiles
without requiring the local collection driver. They rebuild as necessary
before launching each worker; use the fixed checkout and keep the measurement
host idle. The original collection used the equivalent frozen harness/spec
without per-profile rebuilds. The loop stops on a failed command. Inspect every saved candidate status, true residual,
count, input hash and binary identity before using a performance comparison.

.. code-block:: python

   from pathlib import Path
   import json
   import math
   import subprocess
   import sys

   root = Path.cwd()
   groups = [
       ("cpu-release", "cpu-dense-f64-v1", "native,numpy-out,torch-eager-out", "cpu", 3),
       ("cpu-release", "cpu-csr-f64-v1", "native,scipy-out,torch-eager-out", "cpu", 1),
       ("cpu-blas", "cpu-dense-f64-v1", "native,native-blas,numpy-out,torch-eager-out", "cpu", 3),

       ("cuda-release", "cuda-csr-f64-v1", "cuda-native,torch-cuda-eager", "cuda", 1),
       ("cuda-release", "sparse-solvers", "cuda-native,torch-cuda-eager", "cuda", 1),
       ("cpu-release", "sparse-solvers", "native-cg,native-pcg,scipy-cg,scipy-pcg,scipy-lu-total,scipy-lu-reuse", "cpu", 1),
   ]
   configs = [
       (*group, m, scope)
       for group in groups
       for m in (("none",) if group[0] == "cpu-release" and group[1] == "sparse-solvers" else ("none", "jacobi"))
       for scope in ("prepared", "api")
   ]
   for pass_id in (1, 2):
       for preset, suite, candidates, device, repetitions, m, scope in (configs if pass_id == 1 else reversed(configs)):
           python = root / (".venv-cuda" if device == "cuda" else ".venv") / "bin/python"
           name = f"{preset}-{suite}-{m}-{scope}-r{pass_id:02}"
           output = root / "build/performance-optimization/reproduced" / f"{name}.json"
           flags = (
               f"--implementations {candidates} --seed 20261015 --warmups 3 "
               f"--algorithm standard --fused --preconditioner {m} "
               "--rtol 1e-8 --atol 1e-12 --maxiter 2000 --residual-refresh 50"
           )
           if device == "cuda":
               flags += " --device cuda --cuda-device 0"
           command = [
               "taskset", "-c", "0", "make", "pyprof", f"PRESET={preset}",
               f"PYTHON={python}", "JOBS=2", f"PYPROF_SUITE={suite}",
               "PYPROF_THREADS=1", f"PYPROF_SCOPE={scope}", "PYPROF_ROUNDS=30",
               f"PYPROF_REPETITIONS={repetitions}", f"PYPROF_OUTPUT={output}",
               f"PYPROF_ARGS={flags}",

           subprocess.run(command, check=True)
           artifact = json.loads(output.read_text())
           for case in artifact["cases"]:
               assert {entry["name"] for entry in case["results"]} == set(candidates.split(","))
               for entry in case["results"]:
                   assert entry["status"] == "measured" and entry["solver_status"] == "converged"
                   assert math.isfinite(entry["true_residual_norm"])
                   assert entry["true_residual_norm"] <= entry["residual_threshold"] * (1 + 64 * sys.float_info.epsilon)

Baseline profiling observations
-------------------------------

Separate Nsight Systems 2025.5.2 captures used the same frozen CUDA binary,
seed, float64 dense-1024 fixture and Jacobi policy. Each captured 10 calls after
three warmups. All before/after independent residual gates passed; each solve
performed four updates and six matvecs. These instrumented diagnostics are not
part of the 52 framework artifacts or their rankings.

.. csv-table:: Completed diagnostic wall medians, milliseconds
   :header: "Kernel", "probe / scope", "median ms"

   "native", "workspace construction + destruction", "0.897"
   "cuBLAS", "workspace construction + destruction", "2.415"
   "native", "solve / prepared", "1.350"
   "cuBLAS", "solve / prepared", "1.061"

The native workspace capture recorded 70 ``cudaMalloc`` and 70 ``cudaFree``
calls, plus 10 ``cudaMallocHost`` / ``cudaFreeHost`` pairs. The cuBLAS workspace
capture recorded 100 / 110 device allocation/free calls and 160 event
creation/destruction pairs, including provider internals. This measures real
per-call lifecycle; reusing a prepared workspace changes the scope.

In the cuBLAS API solve capture, ``cudaMallocHost`` consumed 7.108 ms and
``cudaFreeHost`` 3.006 ms across ten calls, with per-call medians 0.583 and
0.265 ms. Together they accounted for 26.3% of recorded CUDA API duration.
Their eight-byte storage was used only for scalar readback followed immediately
by a stream fence. This motivates testing workspace-owned pageable scalar
storage while retaining explicit completion and lifetime guarantees; pageable
``cudaMemcpyAsync`` may itself block, as described in the
`CUDA 12.8.1 API synchronization documentation
<https://docs.nvidia.com/cuda/archive/12.8.1/cuda-runtime-api/api-sync-behavior.html>`_.

Both prepared captures recorded 170 ``cudaMemcpyAsync`` and 190
``cudaStreamSynchronize`` calls for ten solves, including the profiler driver's
completion fences. No allocation/free calls occurred in these prepared ranges.
Recorded stream synchronization consumed 72.6% / 75.4% of CUDA API duration for
native / cuBLAS. This motivates an explicit device control mode; it does not
establish an achievable speedup. CUDA API waiting overlaps GPU work, and these
API durations, kernel durations and independently sampled phase medians must
not be added or subtracted as a latency decomposition.

Captures and diagnostic JSON are retained under
``build/performance-optimization/profiles/baseline-*.{json,nsys-rep,sqlite}``,
with ``*_cuda_api_sum.csv`` and ``*_cuda_gpu_kern_sum.csv`` exports. Use
:doc:`../benchmarks` for the public profiling command. CPU disassembly of the
baseline generic GNU 16 ``-O3`` dense kernel shows SSE2 packed double operations;
the optimization question is vector reuse and row blocking, not whether the
baseline is entirely scalar. No CPU hardware-counter measurement is claimed.
